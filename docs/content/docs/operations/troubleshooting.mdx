## Start here

```bash
teldrive check --config /etc/teldrive/config.toml
```

Compose:

```bash
docker compose run --rm teldrive check
docker compose logs --tail=300 teldrive
```

Temporary debug logging:

In a YAML configuration file:

```yaml
logging:
  log-level: debug
  log-format: text
```

Return to `info` after investigating. Debug logs may contain sensitive operational details; redact them before sharing.

## File logging

Console logs remain enabled. To also write to a file, add this to `config.toml`:

```toml
[logging]
log-level = "info"
log-format = "json"
log-file = "/var/log/teldrive/teldrive.log"
```

Or set `TELDRIVE_LOGGING_LOG_FILE=/var/log/teldrive/teldrive.log`. The file uses the configured log level and format, without terminal color codes.

For a host service running as `teldrive`, create the parent directory first:

```bash
sudo install -d -o teldrive -g teldrive -m 0700 /var/log/teldrive
```

New files are created with mode `0600`. Existing files keep their permissions and must be writable by the service user. Teldrive appends on startup; it does not truncate the file. A missing or unwritable parent directory prevents startup.

For the official container image, create a writable directory owned by UID/GID `65532:65532` and mount it into the container:

```bash
sudo install -d -o 65532 -g 65532 -m 0700 /srv/teldrive/logs
```

Add these settings to the Teldrive Compose service:

```yaml
services:
  teldrive:
    environment:
      TELDRIVE_LOGGING_LOG_FILE: /var/log/teldrive/teldrive.log
    volumes:
      - /srv/teldrive/logs:/var/log/teldrive
```

Adjust ownership for rootless containers and apply the required bind-mount labels on SELinux hosts.

There is no automatic rotation or size limit. Prefer console-log collection when available. If rotating the file by renaming it, restart Teldrive to reopen the configured path; otherwise it continues writing to the old file. Monitor disk usage and keep log files private.

## Log rotation, retention and size

Rotation belongs to the host, not to Teldrive. The process writes to stderr; whatever collects that stream owns size limits and retention.

- **Container.** Docker's `json-file` driver rotates the container log. On the current installation `docker inspect teldrive` reports `max-size=10m` and `max-file=3`, and `docker info` reports the same `json-file` driver. `docker inspect teldrive` reports the log path; its size must stay below `max-size` converted to bytes.
- **Host service.** A systemd unit with `StandardOutput=journal` is bounded by journald. Check the budget with `journalctl --disk-usage` and the limits in `journald.conf`.
- **Application file log.** `log-file` is opt-in and append-only. New files are mode `0600`; Teldrive never rotates or truncates them. If you enable it, add host rotation (logrotate with `copytruncate`, or a size-bounded sink) first.

Check the effective sink at any time:

```bash
docker inspect teldrive --format '{{json .HostConfig.LogConfig}}'
docker info --format '{{.LoggingDriver}}'
systemctl show <unit> -p StandardOutput -p StandardError
journalctl --disk-usage
```

Redaction applies to paths Teldrive writes: the server sinks and the Teldrive rclone backend redact local and remote paths. Core rclone operations outside that backend can still log generic object paths; treat those log lines as sensitive when sharing.

## Profiler endpoint

Teldrive mounts no profiling endpoint, including Go `net/http/pprof`. Do not add one to a deployed server.

The rclone mount has an RC profiler path (`/debug/pprof/`), but it is reachable only when the RC server is enabled and authenticated. Never enable RC with its no-auth flag on a host that is reachable by others: that would expose the profile, process arguments and environment.

## Teldrive exits immediately

Check the first error. Common causes:

- missing/unreachable PostgreSQL;
- signing key shorter than 32 characters;
- invalid `security.data-key`;
- invalid proxy/MTProxy combination;
- invalid encryption key/version configuration.

Generate a compatible data key only for a new installation:

```bash
openssl rand -base64 32
```

Do not replace a production data key; existing encrypted values depend on it.

## Container is unreachable

Inside a container, listen on all container interfaces:

```bash
TELDRIVE_HTTP_ADDRESS=0.0.0.0:8080
```

Publish intentionally, for example host loopback only:

```yaml
ports:
  - "127.0.0.1:8080:8080"
```

## PostgreSQL connection failure

```bash
pg_isready -h postgres -p 5432 -U teldrive -d teldrive
```

Check host/service name, port, credentials, database, `sslmode`, networking, readiness, and connection limits. In Compose, use the PostgreSQL service name, not `localhost`.

## Login fails behind HTTPS

Verify:

- proxy sends `X-Forwarded-Proto: https`;
- proxy source is listed in `http.trusted-proxies`;
- users access one canonical HTTPS origin.

See [Reverse proxy and HTTPS](/deployment/reverse-proxy).

## Login disappears after restart

Check that these did not change:

```text
security.signing-key
security.data-key
```

Also verify PostgreSQL data is persistent.

## Live progress updates only after refresh

SSE is being interrupted or buffered. Check proxy response buffering, read/idle timeouts, CDN/load-balancer timeouts, and repeated EventSource reconnects in browser developer tools.

## Upload fails at a fixed duration

Compare timeout limits across:

```text
client → CDN/load balancer → reverse proxy → Teldrive
```

Teldrive defaults to one-hour HTTP read/write timeouts.

## Slow uploads

Check CPU, network, Telegram retry/rate-limit errors, proxy overhead, and BLAKE3 hashing before increasing:

```yaml
telegram:
  upload-threads: 8
```

Increase gradually.

## Slow downloads

Start from defaults:

```yaml
telegram:
  download-read-buffers: 32
  download-read-parallel: 4
  download-bots: 0
```

Tune parallelism only after ruling out client/proxy/host bottlenecks. Add bots only after normal downloads work.

## Proxy/MTProxy config rejected

Use one proxy mode only.

Standard proxy:

```yaml
telegram:
  proxy: socks5://proxy.example.com:1080
```

MTProxy:

```yaml
telegram:
  mtproxy:
    address: proxy.example.com:443
    secret: YOUR_SECRET
```

MTProxy address and secret must both be present.

## Encryption errors after rotation

Keep old key versions referenced by existing files:

```yaml
encryption:
  active-key-version: 2
  keys:
    1: OLD_KEY
    2: NEW_KEY
```

Test both a new upload and an old download.

## Problems only with multiple instances

Verify every process shares the same database/schema and security/encryption keys. Also check aggregate PostgreSQL connections, worker roles, SSE load-balancing, bot rotation backend, and version skew.

## Report useful diagnostics

Include:

- `teldrive version`;
- deployment method;
- redacted relevant config;
- first meaningful log error;
- result of `teldrive check`;
- exact reproduction steps.
